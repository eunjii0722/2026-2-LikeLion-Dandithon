# 시연 기록 준비와 실행

이 자료는 **실제 사진에 대한 Gemini 응답과 실제 ASOS 조회 결과**를, **가상 사용자 이용 이력**에 연결한 시연 자료다. 실제 농가의 한 나무를 같은 날짜에 연속 촬영한 기록이나 실제 사용자 활동이라고 주장하지 않는다. 날짜·주차는 시연용 지정값이며 원본 사진의 촬영일이 아니다. 서비스 화면에는 별도의 시연 배지를 추가하지 않았다.

## 데이터 출처

- `plan.json`: 지정 날짜·주차, 예상 단계, 가상 편지 7통, 가상 농부 메모. 예상 단계는 모델 입력에 넣지 않는다.
- `records.json`: 사진 경로·SHA-256·크기, 사용 모델, 호출 시각, HTTP 상태, **기존 API가 반환한 Vision 7개 필드와 날씨·Diary 응답**, 실제 Diary 요청 및 반영 편지 ID. 키나 사진 Base64는 보관하지 않는다.
- `../diaries.json`: 성공한 Diary 응답 4개. 제목·본문·단어장·근거는 보존된 원본 응답과 동일하며, `photo.url`만 제공된 사진 경로로 연결했다. 원본과 달랐던 18·21·28주차 본문은 API 재호출 없이 `records.json`의 성공 응답에서 복구했다.
- `../../public/demo/history.json`: 기존 다섯 localStorage 키 형식의 가상 이용 이력. 과거 편지 7통은 모두 사용 처리, 미사용 편지 0통, 실제 일기에서 골라 저장한 것으로 설정한 단어 3개. 생성 일기와 채팅 이력은 빈 배열이다.
- `../trees.json`: `tree-1.currentWeek=39`, `harvestWeek=41`.

2026-11-03에 로컬 `/api/vision` 4회, `/api/weather` 4회, `/api/diary` 4회를 실제 호출했고 모두 HTTP 200이었다. 모델은 기존 서버의 `gemini-3.5-flash-lite`를 사용했다. 과거 4개 일기는 모두 사용자의 편지 내용을 반영한 본문을 반환했다. 기존 프롬프트·API·관측값 해석 로직은 변경하지 않았다.

| --- | --- | --- | --- | --- | --- |
| 18 | 2026-05-02 | spring-flowering.jpg | 개화 | 개화 | 높음 |
| 21 | 2026-05-23 | spring-fruit-set.jpg | 착과 | **착색** | 보통 |
| 28 | 2026-07-11 | summer-fruit-growth.jpg | 비대 | 비대 | 높음 |
| 35 | 2026-08-29 | summer-fruit-coloring.jpg | 착색 | 착색 | 보통 |

21주차 모델은 작은 열매의 붉은빛을 관찰하고 착색으로 판단했다. 이 결과를 착과로 수정하거나 원하는 단계가 나올 때까지 재호출하지 않았다. 자세한 불확실성은 `records.json`의 `uncertain_points`에 보존했다. 사진에 주변 나무가 함께 나타나므로 네 일기 모두 `photoType: "orchard"`, `farmerConfirmed: false`다. 메모는 사진 범위를 설명하는 가상 기록이며 농부의 실제 현장 확인을 뜻하지 않는다.

## 기상청 자료

기존 서비스의 기상청 ASOS 청송군 **276번 관측지점**을 사용했다. 아래 기온은 °C, 강수량은 mm다.

| 날짜 | 최고 | 최저 | 강수량 | 일기에 전달한 weather |
| --- | --- | --- | --- | --- |
| 2026-05-02 | 26 | 7 | 누락 | `null` |
| 2026-05-23 | 20.4 | 12.2 | 0 | `{ "tempMax": 20.4, "tempMin": 12.2, "rainMm": 0 }` |
| 2026-07-11 | 34.9 | 21.3 | 누락 | `null` |
| 2026-08-29 | 30.4 | 23 | 28.5 | `{ "tempMax": 30.4, "tempMin": 23, "rainMm": 28.5 }` |

5월 2일·7월 11일의 기온은 `partialWeather`에만 들어 있다. 강수량을 0으로 추정하지 않았으며 부분 기온도 일기 API에 보내지 않았다. 두 날짜의 완전한 날씨는 준비하지 못한 상태이고, 원래 조회 응답과 `rain_missing` 사유는 출처 파일에 남아 있다. 다른 날짜의 관측값으로 대체하지 않는다. 제공된 사진과 이 날짜의 날씨가 실제로 같은 현장에서 동시에 기록됐다는 의미는 아니다.

## 발표 전 명시적 초기화

1. 앱을 실행하고 **별도의 빈 브라우저 프로필**에서 해당 앱 주소를 연다. 기존 개인 사용 프로필의 저장소를 지울 필요가 없다.
2. 그 페이지의 개발자 도구 Console에서 다음 코드를 한 번 실행한다.

```js
const { initializeDemo } = await import("/demo/initialize.js");
await initializeDemo();
```

3. 반환값의 `ok: true`를 확인한다. 홈·타임라인·편지·단어장은 같은 탭에서 바로 갱신된다. 새로고침 후에도 유지된다.

`selectedTreeId`, `letters`, `generatedDiaries`, `savedWords`, `chatHistory` 중 **하나라도 이미 존재하면 중단**한다. 빈 배열, `null`, 손상된 JSON도 기존 데이터로 취급한다. 강제 덮어쓰기 기능이나 자동 초기화는 없다. 실패한 저장은 이번 실행에서 쓴 값만 되돌리며, 복구도 실패하면 별도 오류를 반환한다. 무관한 localStorage 키는 건드리지 않는다. 모듈을 import하는 것만으로는 쓰기 작업이 발생하지 않는다.

과거 일기는 정적 JSON에 한 번만 존재하고 `generatedDiaries`에는 중복 복사하지 않는다. 정적 일기는 `markLetterUsed()`의 대상이 아니므로 과거 편지의 `usedInDiaryId`는 **명시적 초기화용 가상 이력**으로 설정했다. 그 제약을 우회하도록 공통 저장 함수를 바꾸지 않았다. 앞으로 실제 농부 화면에서 생성·저장하는 일기는 기존 `addGeneratedDiary()` 성공 후 `markLetterUsed()`로 편지를 사용 처리한다.

다른 기기·브라우저·프로필·origin(포트 포함) 사이에는 동기화되지 않는다. 발표 전용 프로필은 발표가 끝날 때까지 유지한다. 다시 처음부터 연습하려면 다른 빈 프로필을 사용한다.

## 브라우저 시연 순서

1. 홈에서 홍이와 최근 35주차 일기를 확인한다.
2. 타임라인에서 18 → 21 → 28 → 35주차 사진·일기를 열고, ‘이 일기의 근거’를 펼친다. 21주차는 실제 응답대로 **착색**이다.
3. 편지 화면에서 과거 편지 7통의 ‘답장 받음’을 확인한다. 39주차 편지는 없다.
4. 단어장에서 ‘마이’, ‘우째’, ‘쪼매’를 확인하고 일기 속 단어 뜻풀이도 확인한다.
5. `/farmer`에서 `public/images/demo/autumn-demo.jpg`를 직접 업로드한다. 주변 나무도 담긴 사진이므로 **과수원 공통(orchard)**을 선택하고, 주차 **39**, 관찰 날짜 **2026-09-26**을 입력한다. 실제 확인하지 않았다면 농부 확인 체크박스는 체크하지 않는다.
6. ‘분석하기’를 눌러 실제 응답을 기다린다. 착색·수확기·판단 불가 등 반환된 결과를 그대로 사용하며 수확기를 강제하지 않는다.
7. 날씨 조회 완료 후 ‘이번 주 일기 만들기’를 누른다. 미반영 편지가 없으므로 빈 배열 letters: []가 전달된다.
8. **생성 성공뿐 아니라 저장 성공 안내까지** 확인한다. 홈·타임라인·`/diary/39`에 새 일기가 나오고 기존 편지 7통의 답장 이력은 유지되는지 확인한다. 41주차는 여전히 잠긴 수확 예정이다.

39주차 Vision·Diary는 준비 과정에서 실제 호출하지 않았고 사전 생성 결과를 저장하지 않았다. 따라서 시연 당일 응답 성공은 API 키·네트워크·한도에 따라 달라질 수 있다. 저장 실패 시 편지를 사용 처리하지 않는 기존 흐름을 유지한다.

## 재현과 검증

이미 성공한 결과가 준비되어 있으므로 발표 준비에 API 재호출은 필요 없다. 출처를 재현하거나 중단된 준비를 이어갈 개발 작업에만 다음을 사용한다.

```powershell
# 별도 터미널: 기존 .env.local을 사용하는 로컬 서버
npm run dev -- --hostname 127.0.0.1 --port 3020

# 기록된 성공 응답은 재사용하고, 아직 성공하지 않은 단계만 호출
node scripts/prepare-demo.mjs http://127.0.0.1:3020
```

이 스크립트는 `plan.entries`의 봄·여름 4개만 처리한다. 성공한 사진의 해시나 Diary 요청이 달라졌다면 중단한다. 4개 일기가 모두 성공해야 정적 일기·초기화 이력을 갱신한다. API 실패를 임의의 일기로 채우지 않는다. 기존 호출 결과를 지우고 실행하면 유료 API를 다시 호출할 수 있으므로 출처 파일을 임의 삭제하지 않는다. 날씨 조회 실패도 `null`과 사유로 보존하며 자동으로 임의 값을 만들거나 다른 날짜로 대체하지 않는다.

최초 시연 데이터 준비 시 검증 결과:

- `npm run lint`: 오류 0, 기존 `<img>` 경고 4개.
- `npm run build`: 통과.
- `node --test tests/*.test.mjs`: **108개 통과**. 기존 94개 유지, 시연 검증 14개 추가. 고정된 과거 목업 기대값은 새 데이터에 맞췄고, 특별 소식·미래 일기 차단 등의 회귀 검사는 유지했다.
- 실제 Chrome 격리 프로필: **8개 검증 그룹 통과**. 초기화·재실행 보호·새로고침·홈·타임라인·일기 근거·편지·단어장·320px/390px 화면을 확인했다. 가을 실제 API는 호출하지 않았다.
- 편지 없는 가을 생성 후 일기 추가·홈 선택·기존 편지 이력 유지·41주차 잠금은 **메모리 저장소와 모킹한 API의 자동 테스트**로 확인했다. 그 결과를 실제 Gemini 생성 기록이라고 보관하지 않는다.

이전 가상 16·18주차와 우박 특별 소식은 실행 데이터에서 제거했다. 기존 컴포넌트의 과거 Mock 파일은 삭제하지 않았고 특별 소식 계약 회귀 검사에서 계속 사용한다. 서비스 화면·API·Gemini 프롬프트·공통 저장소 함수·패키지는 수정하지 않았다.

현재 홈 상단은 최근 일기와 분리하여 현재 주차 기준의 ‘가을 · 39주차’를 표시한다. 39주차 일기가 없으면 새로운 성장 소식을 기다린다는 안내를 표시하고, 최근 나무 일기는 ‘35주차 · 여름’으로 별도 표시한다. 생성 후 최근 일기는 39주차로 갱신된다. 누락·미래 일기 화면은 해당 주차보다 이전인 최신 일반 일기로 이동하거나 타임라인으로 돌아갈 수 있다. 이전 일기가 없으면 타임라인 이동만 제공한다.

이미 초기화한 브라우저의 기존 편지는 자동으로 삭제하지 않는다. 이번 7통 구성을 확인하려면 별도의 빈 프로필에서 초기화한다. 기존 데이터 보호 정책은 유지한다.

## 편지·홈·상세 이동 수정 후 검증

- 편지는 총 7통, 미사용 0통이며 가을 요청은 letters: []로 처리한다.
- lint 오류 0(기존 이미지 경고 4), build 통과.
- 전체 자동 테스트 **112개 모두 통과**. 원본 일치 검사 실패는 아래와 같이 화면용 본문을 원본으로 복구하여 해결했다. 테스트 코드는 변경하지 않았다.
- 별도 Chrome 프로필에서 7개 그룹 통과: 현재 계절과 최근 일기 구분, 누락·미래·나무 미선택 이동, 지난 일기 실제 이동, 가상 39주차 저장 후 같은 탭 갱신, 35주차 유지, 41주차 잠금, 320px/390px 레이아웃.
- 39주차 생성은 모킹한 API 및 격리된 브라우저 데이터로만 검증했으며 실제 Gemini 호출이나 사전 생성 기록 저장은 하지 않았다.

## 원본 일치 검사 복구

실패한 검사는 `static diaries preserve API output exactly except the linked photo URL`이다. 사진 URL 연결을 제외한 전체 일기를 성공 API 응답과 비교한다. 제목과 `dialectWords`는 동일했고 다음 본문 차이가 있었다.

- 18주차: 원본의 “농부 확인 전 단계라 개별 나무의 상태나 수확 적기가 따로 기록되지는 않았어.” 문장이 누락되어 복구했다.
- 21주차: 원본의 “보이는데, 지금은 농부 확인 전 상태야.”가 “보인데이.”로 변경되어 원본으로 복구했다.
- 28주차: 추가 대조에서 원본의 “농부 확인 전 상태이며,” 누락도 발견해 복구했다. 테스트가 첫 불일치에서 중단되므로 앞선 실패에서는 드러나지 않았던 차이다.
- 35주차: 원본과 동일해 변경하지 않았다.

`records.json`, `plan.json`, `public/demo/history.json`, 해당 테스트 파일은 작업 전후 SHA-256이 동일하다. 원본·관측자료·편지 이력을 수정하지 않았다. 원본 `records.json`의 SHA-256은 `6a1a1d3f525f26b602871e2f2a7bc183c70cec0dadbea7ea8f73ebe1483db61f`이다.

복구 후 lint(기존 이미지 경고 4개, 오류 0), build, 자동 테스트 112개, `git diff --check`를 통과했다. 이번 복구에서 브라우저 검사를 재실행하지 않았으며 앞의 브라우저 결과는 홈·내비게이션 수정 당시 결과다.
