# 현재 게시본 안내

현재 화면은 원본 API 응답에 명시적인 게시용 교정을 합성한다. 원본은 변경하지 않았으며 아래 원본 복구 기록은 이전 단계의 이력이다. 최신 말투·내비게이션 변경과 전체 문구 전후 비교는 [EDITORIAL.md](./EDITORIAL.md)를 확인한다.

# 시연 기록 준비와 실행

이 자료는 **실제 사진에 대한 Gemini 응답과 실제 ASOS 조회 결과**를, **가상 사용자 이용 이력**에 연결한 시연 자료다. 실제 농가의 한 나무를 같은 날짜에 연속 촬영한 기록이나 실제 사용자 활동이라고 주장하지 않는다. 날짜·주차는 시연용 지정값이며 원본 사진의 촬영일이 아니다. 서비스 화면에는 별도의 시연 배지를 추가하지 않았다.

## 데이터 출처

- `plan.json`: 지정 날짜·주차, 예상 단계, 가상 편지 7통, 가상 농부 메모. 예상 단계는 모델 입력에 넣지 않는다.
- `records.json`: 사진 경로·SHA-256·크기, 사용 모델, 호출 시각, HTTP 상태, **기존 API가 반환한 Vision 7개 필드와 날씨·Diary 응답**, 실제 Diary 요청 및 반영 편지 ID. 키나 사진 Base64는 보관하지 않는다.
- `../diaries.json`: 원본 Diary 응답 4개에 editorial.json의 제목·본문·단어장 교정을 합성한 게시본. 사진 URL과 evidence는 그대로 유지한다. 이전 단계에서 원본 복구를 완료한 뒤 이번에 교정 계층을 분리했다.
- `../../public/demo/history.json`: 기존 다섯 localStorage 키 형식의 가상 이용 이력. 과거 편지 7통은 모두 사용 처리, 미사용 편지 0통, 실제 일기에서 골라 저장한 것으로 설정한 단어 3개. 게시용 일기 4편을 generatedDiaries에 담고 채팅 이력은 빈 배열로 둔다. 별도 dandithon.demoState 키는 시연 시점(version: 1, treeId: tree-1, currentWeek: 39, asOf: 2026-09-26)을, dandithon.adoption 키는 가상 분양 시점(2026-04-04)을 보존한다. 두 날짜의 차이인 25주가 시연의 함께한 기간이다.
- `../trees.json`: `tree-1.currentWeek=39`, `harvestWeek=41`. `photo`는 분양 소개 사진(`baby_apple_tree.jpg`)이며 나무 목록·프로필에만 쓴다. 성장 사진이 아니므로 일기·홈에 쓰지 않는다.

2026-11-03에 로컬 `/api/vision` 4회, `/api/weather` 4회, `/api/diary` 4회를 실제 호출했고 모두 HTTP 200이었다. 모델은 기존 서버의 `gemini-3.5-flash-lite`를 사용했다. 과거 4개 일기는 모두 사용자의 편지 내용을 반영한 본문을 반환했다. 기존 프롬프트·API·관측값 해석 로직은 변경하지 않았다.

| 주차 | 지정 관찰 날짜 | 사진 | 예상 단계 | 실제 Vision 단계 | 확신도 |
| --- | --- | --- | --- | --- | --- |
| 18 | 2026-05-02 | spring-flowering.jpg | 개화 | 개화 | 높음 |
| 21 | 2026-05-23 | spring-fruit-set.jpg | 착과 | **착색** | 보통 |
| 28 | 2026-07-11 | summer-fruit-growth.jpg | 비대 | 비대 | 높음 |
| 35 | 2026-08-29 | summer-fruit-coloring.jpg | 착색 | 착색 | 보통 |

21주차 모델은 작은 열매의 붉은빛을 관찰하고 착색으로 판단했다. 이 결과를 착과로 수정하거나 원하는 단계가 나올 때까지 재호출하지 않았다. 화면의 ‘착과’는 사람이 생육 시기를 고려해 `editorial.json`의 `displayStage`로 보정한 게시용 표시이며, `evidence.growthStage`는 착색 그대로다. 일기의 ‘이 일기의 근거’에서 둘을 구분해 보여 준다. 자세한 불확실성은 `records.json`의 `uncertain_points`에 보존했다. 사진에 주변 나무가 함께 나타나므로 네 일기 모두 `photoType: "orchard"`, `farmerConfirmed: false`다. 메모는 사진 범위를 설명하는 가상 기록이며 농부의 실제 현장 확인을 뜻하지 않는다.

## 기상청 자료

기존 서비스의 기상청 ASOS 청송군 **276번 관측지점**을 사용했다. 아래 기온은 °C, 강수량은 mm다.

| 날짜 | 최고 | 최저 | 강수량 | 일기에 전달한 weather |
| --- | --- | --- | --- | --- |
| 2026-05-02 | 26 | 7 | 누락 | `null` |
| 2026-05-23 | 20.4 | 12.2 | 0 | `{ "tempMax": 20.4, "tempMin": 12.2, "rainMm": 0 }` |
| 2026-07-11 | 34.9 | 21.3 | 누락 | `null` |
| 2026-08-29 | 30.4 | 23 | 28.5 | `{ "tempMax": 30.4, "tempMin": 23, "rainMm": 28.5 }` |

5월 2일·7월 11일의 기온은 `partialWeather`에만 들어 있다. 강수량을 0으로 추정하지 않았으며 부분 기온도 일기 API에 보내지 않았다. 두 날짜의 완전한 날씨는 준비하지 못한 상태이고, 원래 조회 응답과 `rain_missing` 사유는 출처 파일에 남아 있다. 다른 날짜의 관측값으로 대체하지 않는다. 제공된 사진과 이 날짜의 날씨가 실제로 같은 현장에서 동시에 기록됐다는 의미는 아니다.

## 발표 전 명시적 초기화

1. 앱을 실행하고 **별도의 빈 브라우저 프로필**에서 해당 앱 주소를 연다. 기존 개인 사용 프로필의 저장소를 지울 필요가 없다.
2. 그 페이지의 개발자 도구 Console에서 다음 코드를 한 번 실행한다.

```js
const { initializeDemo } = await import("/demo/initialize.js");
await initializeDemo();
```

3. 반환값의 `ok: true`를 확인한다. 홈·타임라인·편지·단어장은 같은 탭에서 바로 갱신된다. 새로고침 후에도 유지된다.

`selectedTreeId`, `letters`, `generatedDiaries`, `savedWords`, `chatHistory`, `dandithon.demoState` 또는 `dandithon.adoption` 중 **하나라도 이미 존재하면 중단**한다. 빈 배열, `null`, 손상된 JSON도 기존 데이터로 취급한다. 강제 덮어쓰기 기능이나 자동 초기화는 없다. 실패한 저장은 이번 실행에서 쓴 값만 되돌리며, 복구도 실패하면 별도 오류를 반환한다. 무관한 localStorage 키는 건드리지 않는다. 모듈을 import하는 것만으로는 쓰기 작업이 발생하지 않는다.

정적 JSON은 원본/게시본 검증용으로 보존하되 일반 사용자 조회에는 자동 합치지 않는다. 명시적 초기화가 게시용 4편을 `generatedDiaries`에 복사한다. 과거 편지는 실제 사용자 활동이 아니므로 과거 편지의 `usedInDiaryId`는 **명시적 초기화용 가상 이력**으로 설정했다. 그 제약을 우회하도록 공통 저장 함수를 바꾸지 않았다. 앞으로 실제 농부 화면에서 생성·저장하는 일기는 기존 `addGeneratedDiary()` 성공 후 `markLetterUsed()`로 편지를 사용 처리한다.

다른 기기·브라우저·프로필·origin(포트 포함) 사이에는 동기화되지 않는다. 발표 전용 프로필은 발표가 끝날 때까지 유지한다. 다시 처음부터 연습하려면 다른 빈 프로필을 사용한다.

## 브라우저 시연 순서

1. 홈에서 홍이와 최근 35주차 일기를 확인한다.
2. 타임라인에서 18(개화) → 21(착과) → 28(비대) → 35(착색)주차 사진·일기를 열고, ‘이 일기의 근거’를 펼친다. 21주차의 착과는 게시용 보정이고 실제 AI 판정 원본은 **착색**임을 근거에서 함께 보여 준다.
3. 편지 화면에서 과거 편지 7통의 ‘답장 받음’을 확인한다. 39주차 편지는 없다.
4. 단어장에서 ‘마이’, ‘단디’, ‘우째’를 확인하고 일기 속 단어 뜻풀이도 확인한다.
5. `/farmer`에서 `public/images/demo/autumn-demo.jpg`를 직접 업로드한다. 주변 나무도 담긴 사진이므로 **과수원 공통(orchard)**을 선택하고, 주차 **39**, 관찰 날짜 **2026-09-26**을 입력한다. 실제 확인하지 않았다면 농부 확인 체크박스는 체크하지 않는다.
6. ‘분석하기’를 눌러 실제 응답을 기다린다. 착색·수확기·판단 불가 등 반환된 결과를 그대로 사용하며 수확기를 강제하지 않는다. 화면의 ‘수확 직전’은 수확 1~2주 전이라는 시기 표현이고, 실제 AI 결과는 `evidence.growthStage`에 그대로 저장되어 홈 캡션과 일기 근거에 함께 표시된다.
7. 날씨 조회 완료 후 ‘이번 주 일기 만들기’를 누른다. 미반영 편지가 없으므로 빈 배열 letters: []가 전달된다.
8. **생성 성공뿐 아니라 저장 성공 안내까지** 확인한다. 홈·타임라인·`/diary/39`에 새 일기가 나오고 기존 편지 7통의 답장 이력은 유지되는지 확인한다. 41주차는 여전히 잠긴 수확 예정이다.

39주차 Vision·Diary는 준비 과정에서 실제 호출하지 않았고 사전 생성 결과를 저장하지 않았다. 따라서 시연 당일 응답 성공은 API 키·네트워크·한도에 따라 달라질 수 있다. 저장 실패 시 편지를 사용 처리하지 않는 기존 흐름을 유지한다.

## 재현과 검증

이미 성공한 결과가 준비되어 있으므로 발표 준비에 API 재호출은 필요 없다. 출처를 재현하거나 중단된 준비를 이어갈 개발 작업에만 다음을 사용한다.

```powershell
# 별도 터미널: 기존 .env.local을 사용하는 로컬 서버
npm run dev -- --hostname 127.0.0.1 --port 3020

# 기록된 성공 응답은 재사용하고, 아직 성공하지 않은 단계만 호출
node scripts/prepare-demo.mjs http://127.0.0.1:3020
```

이 스크립트는 `plan.entries`의 봄·여름 4개만 처리한다. 성공한 사진의 해시나 Diary 요청이 달라졌다면 중단한다. 4개 일기가 모두 성공해야 정적 일기·초기화 이력을 갱신한다. API 실패를 임의의 일기로 채우지 않는다. 기존 호출 결과를 지우고 실행하면 유료 API를 다시 호출할 수 있으므로 출처 파일을 임의 삭제하지 않는다. 날씨 조회 실패도 `null`과 사유로 보존하며 자동으로 임의 값을 만들거나 다른 날짜로 대체하지 않는다.

최초 시연 데이터 준비 시 검증 결과:

- `npm run lint`: 오류 0, 기존 `<img>` 경고 4개.
- `npm run build`: 통과.
- `node --test tests/*.test.mjs`: **108개 통과**. 기존 94개 유지, 시연 검증 14개 추가. 고정된 과거 목업 기대값은 새 데이터에 맞췄고, 특별 소식·미래 일기 차단 등의 회귀 검사는 유지했다.
- 실제 Chrome 격리 프로필: **8개 검증 그룹 통과**. 초기화·재실행 보호·새로고침·홈·타임라인·일기 근거·편지·단어장·320px/390px 화면을 확인했다. 가을 실제 API는 호출하지 않았다.
- 편지 없는 가을 생성 후 일기 추가·홈 선택·기존 편지 이력 유지·41주차 잠금은 **메모리 저장소와 모킹한 API의 자동 테스트**로 확인했다. 그 결과를 실제 Gemini 생성 기록이라고 보관하지 않는다.

이전 가상 16·18주차와 우박 특별 소식은 실행 데이터에서 제거했다. 기존 컴포넌트의 과거 Mock 파일은 삭제하지 않았고 특별 소식 계약 회귀 검사에서 계속 사용한다. 서비스 화면·API·Gemini 프롬프트·공통 저장소 함수·패키지는 수정하지 않았다.

현재 홈 상단은 최근 일기와 분리하여 현재 주차 기준의 ‘가을 · 생육 39주차’와 ‘함께한 기간 25주차’를 표시한다. 39주차 일기가 없으면 새로운 성장 소식을 기다린다는 안내를 표시하고, 최근 나무 일기는 ‘35주차 · 여름’으로 별도 표시한다. 생성 후 최근 일기는 39주차로 갱신된다. 누락·미래 일기 화면은 해당 주차보다 이전인 최신 일반 일기로 이동하거나 타임라인으로 돌아갈 수 있다. 이전 일기가 없으면 타임라인 이동만 제공한다.

이미 초기화한 브라우저의 기존 편지는 자동으로 삭제하지 않는다. 이번 7통 구성을 확인하려면 별도의 빈 프로필에서 초기화한다. 기존 데이터 보호 정책은 유지한다.

## 편지·홈·상세 이동 수정 후 검증

- 편지는 총 7통, 미사용 0통이며 가을 요청은 letters: []로 처리한다.
- lint 오류 0(기존 이미지 경고 4), build 통과.
- 전체 자동 테스트 **112개 모두 통과**. 원본 일치 검사 실패는 아래와 같이 화면용 본문을 원본으로 복구하여 해결했다. 테스트 코드는 변경하지 않았다.
- 별도 Chrome 프로필에서 7개 그룹 통과: 현재 계절과 최근 일기 구분, 누락·미래·나무 미선택 이동, 지난 일기 실제 이동, 가상 39주차 저장 후 같은 탭 갱신, 35주차 유지, 41주차 잠금, 320px/390px 레이아웃.
- 39주차 생성은 모킹한 API 및 격리된 브라우저 데이터로만 검증했으며 실제 Gemini 호출이나 사전 생성 기록 저장은 하지 않았다.

## 원본 일치 검사 복구

실패한 검사는 `static diaries preserve API output exactly except the linked photo URL`이다. 사진 URL 연결을 제외한 전체 일기를 성공 API 응답과 비교한다. 제목과 `dialectWords`는 동일했고 다음 본문 차이가 있었다.

- 18주차: 원본의 “농부 확인 전 단계라 개별 나무의 상태나 수확 적기가 따로 기록되지는 않았어.” 문장이 누락되어 복구했다.
- 21주차: 원본의 “보이는데, 지금은 농부 확인 전 상태야.”가 “보인데이.”로 변경되어 원본으로 복구했다.
- 28주차: 추가 대조에서 원본의 “농부 확인 전 상태이며,” 누락도 발견해 복구했다. 테스트가 첫 불일치에서 중단되므로 앞선 실패에서는 드러나지 않았던 차이다.
- 35주차: 원본과 동일해 변경하지 않았다.

`records.json`, `plan.json`, `public/demo/history.json`, 해당 테스트 파일은 작업 전후 SHA-256이 동일하다. 원본·관측자료·편지 이력을 수정하지 않았다. 원본 `records.json`의 SHA-256은 `6a1a1d3f525f26b602871e2f2a7bc183c70cec0dadbea7ea8f73ebe1483db61f`이다.

복구 후 lint(기존 이미지 경고 4개, 오류 0), build, 자동 테스트 112개, `git diff --check`를 통과했다. 이번 복구에서 브라우저 검사를 재실행하지 않았으며 앞의 브라우저 결과는 홈·내비게이션 수정 당시 결과다.

## 신규 사용자와 시연 사용자 분리

주차는 두 개념으로 나눈다. 숫자를 서로 빼거나 섞어 계산하지 않는다.

- **함께한 기간(분양 경과 주차)**: 분양 시점부터 지난 주 수. 신규 사용자는 분양 직후 0이다. 분양 완료(`adoptTree`) 때 dandithon.adoption에 시점을 저장하고 `getAdoptionWeeks`로 계산한다. 같은 나무를 다시 분양해도 처음 시점을 유지한다. 화면에는 ‘함께한 기간 N주차’, ‘N주 함께함’으로 표시한다.
- **생육 주차**: tree.startWeek·currentWeek·harvestWeek와 일기·편지의 week. 농부 사진 분석과 일기 생성, 수확까지 남은 주, 진행 막대가 이 값을 쓴다. 나무의 현재 시점은 ‘생육 N주차’로 표시한다. 일기·편지 기록에 붙은 ‘N주차’도 같은 뜻이다.

일반 사용자의 생육 주차는 startWeek(14)에서 시작하며 일기·편지·단어·대화는 빈 상태다. 사용자 일기는 저장된 generatedDiaries만 조회한다. 새 일기가 저장되면 현재 생육 주차는 시작 주차·명시적 시연 주차·저장 일기 주차의 최댓값이 된다. 따라서 새 기록을 미래로 숨기지 않으며, 함께한 기간은 이 때문에 늘어나지 않는다. 생육 주차 계산은 getUserTree에 모았다. 시간이 지나도 생육 주차는 새 일기가 저장될 때만 올라간다.

시연은 최신 일기(35주차)와 현재 시점(39주차)이 다르므로 별도 메타데이터가 필요하다. 기존 다섯 키의 JSON 계약은 바꾸지 않았으며, dandithon.demoState는 초기화만 쓴다. import나 앱 접속만으로 초기화하지 않는다. 일곱 키 모두 사전 검사·경합 검사·롤백 대상이다. 시연 날짜는 가상이므로 함께한 기간은 실제 시각과 무관하게 asOf 기준 25주로 고정된다. 기존 사용자의 데이터를 자동 삭제하거나 이전 시연 브라우저를 자동 마이그레이션하지 않는다. 이번 변경 전에 초기화한 브라우저는 dandithon.adoption이 없어 함께한 기간이 0으로 보이므로 별도의 빈 프로필에서 다시 초기화한다.

## 생육 단계 표시와 사진 구분

화면의 단계는 `getDiaryStage` 한 곳에서 정한다. 게시용 보정(`displayStage`) → 시기 표현(수확 1~2주 전 ‘수확 직전’) → AI 판정(`evidence.growthStage`) 순서이며, 원본 판정은 어느 경우에도 바꾸지 않는다. 표시가 원본과 다르면 일기 근거가 ‘화면 표시 단계’와 ‘AI 사진 판정 원본’을 나눠 보여 준다.

| 계절 | 생육 주차 | 표시 | 근거 |
| --- | --- | --- | --- |
| 봄 | 18 | 개화 | AI 판정 |
| 봄 | 21 | 착과 | 사람이 보정한 게시용 표시, AI 원본은 착색 |
| 여름 | 28 | 비대 | AI 판정 |
| 여름 | 35 | 착색 | AI 판정 |
| 가을 | 39 | 수확 직전 | 시기 표현, AI 결과는 라이브 시연에서 따로 저장 |
| 가을 | 41 | 수확 예정(잠금) | 예정 |

사진은 세 종류를 섞지 않는다. 소개 사진(`tree.photo`)은 나무 목록·프로필에만, 성장 사진(일기의 `photo.url`)은 홈·일기·타임라인에 쓴다. 성장 일기가 하나도 없으면 ‘아직 홍이의 사진이 도착하지 않았어요.’를 표시한다. 홈 상단은 이번 주(현재 생육 주차) 일기의 사진만 쓴다. 시연의 39주차처럼 이번 주 일기가 없으면 상단은 ‘39주차 사진이 아직 도착하지 않았어요.’ 안내를 표시하고, 지난 35주차 사진은 아래 최근 일기 카드에만 표시한다. 39주차 일기가 저장되면 상단과 카드 모두 새 사진으로 바뀐다. 분양 신청 화면에는 원래 사진 영역이 없어 새로 만들지 않았다.

## 개발 서버 주의

`npm run dev` 직후 **페이지를 열기 전에** API 라우트를 먼저 호출하면(curl, 스크립트 등) Next.js 16.4.3 Turbopack HMR이 접속마다 재시작 메시지를 보내 페이지가 무한 재로드되고 홈이 ‘불러오는 중’에 멈출 수 있다. 페이지를 먼저 열면 발생하지 않았다. 앱 코드 문제가 아니므로 이런 상태가 되면 개발 서버를 다시 시작한다. 프로덕션 실행(`npm run build` 후 `npm start`)에는 HMR이 없다.

## Chat 지연 진단

개발 모드에서 브라우저 Console의 [chat timing]은 요청 시작, 응답 수신, 저장 완료, React 화면 반영 시간을 기록한다. Network의 Server-Timing에는 서버 전체와 Gemini 처리 시간이 표시된다. 서버 콘솔은 수신 및 Gemini 시작/완료(오류 포함)를 기록한다. 질문·답변·사진·편지·키는 기록하지 않는다. 프로덕션에서는 이 진단을 끈다.

이력 10개·일기 30개 한도와 사진 제외를 유지한다. 8초/20초 지연 안내, 서버 45초에 여유를 둔 클라이언트 55초 취소, 상태별 오류 안내를 적용했다. 요청은 한 번에 하나만 보내고, 화면을 벗어났다 돌아와도 진행 중인 요청을 이어서 표시한다. 답을 받지 못한 마지막 질문은 새로고침 후에도 ‘다시 시도’로 같은 질문을 중복 저장 없이 재요청할 수 있다. timeout을 줄여 속도가 개선됐다고 주장하지 않는다. 설치된 SDK(@google/genai 2.32.0) 소스에서 `timeout_ms`는 시도당 제한으로, `maxRetries: 0`은 재시도 없음으로 적용됨을 확인했으므로 SDK 재시도 누적은 지연 원인에서 제외된다. 실제 Gemini 연결 지연 및 말투 품질은 승인된 실호출 측정이 필요하다.
